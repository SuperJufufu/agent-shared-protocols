# 拆分 playbook

## 什么时候该拆

满足任意两条就值得拆：

- 文档超过约 300 行，或者超过 8 个独立主题。
- 每次任务都要「从头读到尾」，但实际用到的不到 1/5。
- 同一份文档被多个 agent / 多人共享，各自只关心其中一块。
- 文档还在长，且新内容跟旧内容互不相干。

不该拆：读者需要线性读完（教程、README）、只有几十行、主题之间强耦合到没法分开引用。

## 拆分步骤

### 1. 列主题

通读一遍，把内容拆成「一个问题域」的候选。判断标准：**能不能用一句话说清它的 scope，并且这句话里能写出「不包含什么」**。

### 2. 合并与分开

- 合并：总是一起被需要的（端口表 + 启动命令）。
- 分开：总被一起塞进上下文、但其实互不相干的（部署步骤 vs 排障步骤）。
- 边界拿不准时，问一句：「什么任务会只读这一份、不读别的？」答不上来就并入相邻主题。

### 3. 先写路由，再写正文

给每个主题写 `scope` 和 `read_when`。写不出 `read_when` 的主题说明还没想清；`read_when` 里出现「相关」「全部」说明边界太宽。

自检：拿 5 个真实任务，每个任务能否**唯一**命中一份？命中两份以上 → 路由要改；全部命中同一份 → 拆得没意义。

### 4. 原样搬运

按主题把原文章节搬过去，**不改写**。改写在拆分之后单独做，否则一次改动里混了两类风险，出问题难定位。

### 5. 改交叉引用

原文里「见下文第 X 节」改成 `见 03-xxx.md`。索引里只留一句总则，不复制操作步骤。

### 6. 校验

```sh
scripts/check-routing.sh INDEX.md
```

全 `[ok]` 再交付。然后随机挑三个任务走一遍路由，确认读到的正是该读的那份。

### 7. 归档原文

原文移到 `archive/` 或依赖 git 历史。确认新结构可用（通常一周）后再删。

## 反模式

| 反模式 | 为什么坏 | 改法 |
|---|---|---|
| 按章节机械切（第一章一份、第二章一份） | 切出来的每份都不能独立回答一个任务 | 按任务问题域切 |
| 索引变成第二份正文 | 两份内容必然漂移，读者不知道信哪份 | 索引只留路由和总则 |
| 子文档互相抄同一段 | 同一事实两个权威，改一处漏一处 | 留一份，另一处写指针 |
| `read_when` 写成内容摘要 | agent 读完索引就以为懂了，不再读正文 | 写触发场景 |
| 拆完不做反向校验 | 有文档没登记，等于从路由里消失 | 跑 check-routing.sh |
| 为了「完整」保留巨型附录 | 没人读，但每次都被迫考虑要不要读 | 移进单独的参考文档，标清「按需」 |

## 规模参考

| 文档量 | 结构 |
|---|---|
| < 100 行 | 不拆 |
| 100–400 行 | 索引 + 3~6 份子文档 |
| > 400 行 | 索引 + 子文档；某份仍超 300 行就再拆一层 |
| 多主题岛（互不引用） | 每岛一个子索引，顶层只做路由 |

数字只是起点，判据始终是「一次任务需要读多少」。
